# Curriculum, homework and assessment implementation plan

> Use Superpowers executing-plans and the common definition of done in PLANS.md. Final QA (Q03–Q05 and device checks) begins after integrated pre-launch deployment. Acceptance cases here describe future checks; do not write or run tests during these tasks.

**Goal** Staff plan and record learning and families see accurate, clearly attributed results for a selected child. **Architecture** Versioned Next/Vercel handlers, private Supabase Postgres + RLS, responsive PWA and Kotlin/Compose native APK. Read the [product](../specs/product.md) and [integration contracts](../specs/contracts.md).

**Global constraints and files** These are adopted new paths, bound to the checkout by F01. Each stem below maps to `packages/contracts/src/academics/<stem>.ts`, `apps/web/src/server/academics/<stem>.ts`, `apps/web/src/features/academics/<stem>.tsx` and `apps/android/app/src/main/java/de/madrasty/app/academics/<Screen>.kt`. Implement matching `apps/web/src/app/api/v1` handlers; add ordered `supabase/migrations` files with the stated suffixes. Routes omit the shared `/api/v1`; all JSON uses F02 envelopes, idempotency keys for commands, stable IDs and optimistic revisions. In every card, use the active persona, S05 dated class/subject/capability and S02 active child link. Staff read/write only within their grant; parents get private projections for their own selected child. Scope search, reports, count and direct URL identically; on revocation drop private UI state. Use F03 Arabic/German, accessible scores, translated empty/error/loading states, preserved edits on failed save and visible year/class/subject/child context. Before Q01 verify via inspection and F01's type/web/Android builds only. Record evidence in PROGRESS.md.

**Review focus** Publication and actual delivery are independent, enrollment later in a year must materialize missing homework rows, zero must survive serialization, corrections need immutable history, and aggregations need explicit units/source dates.

### E01 — Bilingual subjects and versioned curriculum publishing

**Goal / requirements** R07. Let staff maintain the religious subject catalog and publish class-specific planned lessons. **Depends** S01, S03, S05, F02, F03. **Files** `curriculum`, `CurriculumScreen`, migration `curriculum_versions`. **Scope** Curriculum plans and subject detail. Actual classroom coverage belongs to E02.
- [x] Extend S05's subject table with bilingual descriptions and archive state. Seed Fiqh (الفقه / Fiqh), Seerah (السيرة / Sīra) and Hadith (الحديث / Hadith); maintain stable keys used by offerings. Preserve historical subject references upon archive. Exclude memorization/Tajweed trackers and conflicting preview seed content.
- [x] Add curriculum unit/lesson UUID, offering/class/year, sort order, optional plan date, draft revision, immutable published revisions, localized title/body in Arabic and German and author. Require a valid title and content in the source language. Support an alternate-language version; if absent, label the source language while keeping navigation and notices in the guardian’s chosen language. This avoids requiring teachers to translate their own free text to record a lesson. For school broadcasts use C04’s separate audience/language preview. Always retain the last published revision while editing a new draft. Check authorization and offering/dates when writing.
- [x] Implement `GET/POST /academics/subjects`, `GET/PATCH /academics/subjects/{id}`, `GET/POST /academics/lessons`, `GET/PATCH /academics/lessons/{id}`, `POST /academics/lessons/{id}/publish` {revision} → publication ID/time + current revision. Staff lists accept offeringId; parent reads require childId and return published revision for eligible class only. Parent detail by draft UUID or an unrelated class is concealed. Publishing ordinary lesson content changes the in-app catalog.
- [x] Build subject directory/detail and staff plan/editor/preview/publish on both platforms; parent selects child and reads published lesson in selected locale. Distinguish planned date, published time and classroom-delivery status.

**Acceptance at final QA** Parent of class A reads the previous published revision while a teacher edits a bilingual draft. A source lesson with no German translation stays readable with its source language indicated; an empty source title blocks publication; a teacher assigned only another subject cannot publish. Subject archiving retains existing lesson labels. **DoD** Inspect scoped projections, last-published pointer and bilingual validation and build both surfaces.

### E02 — Record classroom delivery and general activity marks

**Goal / requirements** R07, R09. Record what was taught on a date and support ordinary assessed activities with an explicit score and maximum. **Depends** E01, S03, S05. **Files** `teaching-activity`, `TeachingActivityScreen`, migration `teaching_log_activities`. **Scope** Two distinct entries in the class/subject workspace; neither a homework grade nor an exam score supplies an activity mark.
- [x] Add teaching log (UUID, class/subject/assignment, scheduled lesson or published lesson version optional, actual date, delivered notes, recorded_by, revision). Store actual delivered content separately from planned body and planned date. Validate active teaching assignment and date/roster; repeated teaching of a topic on different dates remains distinct. Keep student-private notes outside family curriculum projections.
- [x] Add activity (UUID, class/subject/year, local date, title, maximum numeric > 0); student activity mark (activity/student unique, score numeric nullable, revision, recorded by/date, visibility). Enforce score between zero and activity maximum. Protect changes to previously visible marks with revision, reason and immutable before/after entry. Retain child/enrollment context from activity date. Define one canonical result projection with source kind `activity`, source record, date, numerator, denominator and revision for E07.
- [x] Implement `GET/POST /academics/teaching-log`, `PATCH /academics/teaching-log/{id}` {revision,actualDate,deliveredNotes,lessonVersionId?}; `GET/POST /academics/activities` {offeringId,date,title,maxScore}; `PUT /academics/activities/{id}/marks/{studentId}` {score,revision,reasonIfCorrection?} → recorded result/visible revision. Family reads through a child-scoped view after a mark is recorded, with no staff-only log notes. Visible correction emits one private `result.published` with sourceKind=activity, change=correction, child/revision; no mark or private note in outbox.
- [x] Build staff teaching log with separate planned-vs-delivered fields, activity roster/editor and parent activity-result detail, including child switch and empty results, on web/Compose.

**Acceptance at final QA** Publishing a lesson does not mark it taught; a different topic/date can be logged with its own author. Activity 0/8 displays as recorded, missing mark is empty, 9/8 is rejected. A correction changes the current display and retains old score/reason for staff. **DoD** Inspect independent table ownership and parent DTO, authorized corrections and both client screens; record builds.

### E03 — Assign homework to the whole class, including later joiners

**Goal / requirements** R08. Every pupil in the class gets exactly one homework roster entry, with membership history for pupils joining later. **Depends** E01, S03, S05. **Files** `homework`, `HomeworkScreen`, migration `homework_roster`. **Scope** Teacher/admin author and parent assignment reader. Homework provides instructions and due dates; the app has no parent upload/submission route.
- [x] Add homework (UUID, class/subject/year, optional lesson FK, title, instructions, issued_on date, due_on date, author, revision); homework roster/grade (homework/student unique, enrollment FK, joined_on date, added_later boolean, score nullable, feedback, revision). On creation lock class and insert rows for all enrolled on issue date. Extend S03 enrollment writes in the same transaction (including imports/bulk enrollment/transfers/rollover as applicable) to insert missing rows for existing homework in the same class/year. For future-effective starts materialize with actual joined_on and filter visibility/counts as-of date. Catch rows already present on E03 rollout; unique key + serialized class coordination prevent races with newly created homework. Later joiners receive even existing past-due work; retain marked/historical rows on exit or re-entry.
- [x] Implement `POST /academics/homework` {offeringId,title,instructions,issuedOn,dueOn,lessonId?} → assignment, rosterCount, revision; `GET /academics/homework?classId=…|childId=…`, `GET/PATCH /academics/homework/{id}` (parent supplies child context; edit uses revision). Enforce valid chronological dates and permission. Parent details include selected child's own assignment, score/feedback if recorded and join-date annotation. Conceal classmates and unpublished/private teacher data.
- [x] Build teacher/admin assignment create/edit/list and read-only family assignment/detail via child's menu on both clients. Include joining date, due date, score-pending text; link authorized staff to E04's grade roster. Instructions appear in ordinary app feeds without a routine email blast.

**Acceptance at final QA** Start with three pupils, add a fourth after due date, retry the enroll command, then transfer the child: the original homework has one row per eligible child, correct joined date and no duplicated outcomes. No row outside the assigned class/year is exposed. Two siblings viewing the same homework see separate score states. **DoD** Inspect transactional insert/backfill, effective-date filters, public routes and both submit-free family views; record builds.

### E04 — Grade homework individually and in a whole-class mark sheet

**Goal / requirements** R08, R09. Teachers record half-point marks and personalized feedback, including zero, in a discoverable grading inbox. **Depends** E03. **Files** `gradebook`, `GradebookScreen`, migration `homework_grading`. **Scope** Authorized teacher with homework.grade or academic supervisor; parent read-only. Ordinary homework grade is visible on confirmed recording.
- [x] Enforce `score numeric` nullable with `score between 0 and 20 and score*2=trunc(score*2)` on stored original precision (never round invalid inputs); validate decimal precision before storage, support localized number input on clients. On visible mark/feedback change require revision + reason, append immutable previous/current values, and emit one `result.published` for correction with sourceKind=homework. Zero, null and unchanged are distinct; feedback omitted means preserve, explicit clear uses null. Protect existing feedback in bulk score-only saves.
- [x] Implement `GET /academics/grading?classId=…` → homework summaries graded/total; `GET /academics/homework/{id}/grades` → scoped paginated full class roster; `PATCH /academics/homework/{id}/grades/{studentId}` {revision,score?,feedback?,reasonIfCorrection?}; `POST /academics/homework/{id}/grades/bulk` {rows:[{studentId,revision,score,reasonIfCorrection?}]} → saved revisions/counts. Validate entire bulk request/permission/row ownership and revisions before a transaction commits; reject invalid/stale rows with field identifiers, keep other local edits. Use published result state for parent reads without sending ordinary new-homework mail.
- [x] Add a dedicated grading inbox under Teacher More, group by homework, link to class sheet and individual feedback editor. Implement class-scoped admin read/authorized edit, parent “grade not recorded yet” vs 0/20 and child-specific feedback on web and Compose. Show only committed save; reports use null-excluding denominators.

**Acceptance at final QA** Submit null, 0, 0.5 and 20, reject -0.5, 9.25 and 20.5; confirm decimal comma input maps to the same wire number. Bulk save preserves an existing individual note and cannot cross classes. A correction to a previously visible mark updates report and family detail with one correction event per child. **DoD** Inspect non-rounding SQL/input validation, individual/bulk DTO distinction, two-client entry points and family serialization; record builds.

### E05 — Review, publish and correct periodic evaluations

**Goal / requirements** R09. Publish a teacher's periodic evaluation for a child with three independent scales, qualitative feedback and a traceable correction. **Depends** E01, S02, S03, S05. **Files** `evaluations`, `EvaluationScreen`, migration `student_evaluations`. **Scope** Academic supervisor/authorized assigned teacher prepares and publishes within capability; guardians see published versions of their child.
- [x] Add evaluation (UUID, student, dated enrollment, offering/subject, period start/end, title, unique pupil/offering/period), draft/current publication pointer and immutable revisions. Participation, understanding, preparation each use smallint 1..5, with strengths and improvement text. Incomplete draft may contain null scales, publishing requires all three. Preserve published snapshot while editing correction.
- [x] Implement `GET/POST /academics/evaluations`, `GET/PATCH /academics/evaluations/{id}` {revision,participation,understanding,preparation,strengths,improvements,…}; `POST /academics/evaluations/{id}/publish` {revision} → current published revision; `POST /academics/evaluations/{id}/correct` {revision,changes,reason} → superseding publication. Revalidate capability, membership, dimensions and revision. Save audit with prior/new values and one `result.published` per child/source revision; payload includes sourceKind=evaluation, change and batch ID as appropriate. Only the API inside the account returns scales/notes.
- [x] Build staff draft/review/publish flow, authorized correction dialog and parent evaluation card with period, three separately named values, strengths and improvement text. Support class or child selection as permitted on both clients and preserve the previous published version during edits.

**Acceptance at final QA** Draft hidden from parent until publish; 0/6 are rejected, min/max scales survive, revoked substitute cannot publish, and a retried correction cannot deliver twice. E07 immediately resolves latest published revision. **DoD** Inspect immutable snapshots, scoped reads, event uniqueness and all platform states; record builds.

### E06 — Announce oral/written exams and publish reviewed results

**Goal / requirements** R09. Keep an exam schedule announcement distinct from publication of individual marks. **Depends** E01, S02, S03, S05. **Files** `exams`, `ExamScreen`, migration `exams_results`. **Scope** Oral and written exams, review, class announcement and private results. No public class marks list.
- [x] Add exam (UUID, offering, date, type oral/written, title, max_points numeric > 0, schedule state, revision), result (exam/student unique, enrollment, score numeric nullable, feedback, draft revision), immutable result publication revisions/batch UUID. Check 0 ≤ score ≤ maximum; incomplete is separate from 0. Revalidate all entered marks on a maximum change; reject maximum edits invalidating published values without reviewed corrections.
- [x] Implement `GET/POST /academics/exams`, `GET/PATCH /academics/exams/{id}`, `POST /academics/exams/{id}/announce` {revision,date} → schedule revision and committed `exam.published`. Changing the published time/date creates one revised announcement with change=reschedule; unannounced drafts have no family alert. Implement `PUT /academics/exams/{id}/marks/{studentId}` {score,feedback,revision}; `POST /academics/exams/{id}/results/publish` {reviewedRows:[{studentId,revision}],revision} → batch ID and published revisions. Validate reviewed cohort, scope and marks atomically; never convert unentered rows into zeros. Snapshot recipients via child IDs, enforce current guardian links at read/delivery.
- [x] Implement `POST /academics/exams/{id}/results/{studentId}/correct` {revision,score,feedback,reason} → immutable replacement, audit, current result. Emit `result.published` with sourceKind=exam, change=initial|correction, batch ID and affected pupil/source revision; C07 groups one batch notification per eligible account with protected deep link. Preserve previous snapshots and supersede stale pending deliveries. Public channels contain no scores.
- [x] Build exam calendar/list, create/announce/reschedule, teacher mark entry/review, explicit batch publish/correction; parent sees child-class announced schedule and individually published score/feedback only. Provide separate draft vs announced vs result-published cues on web and Compose.

**Acceptance at final QA** Parents can see a published schedule while marks remain hidden; rescheduling issues one updated announcement. Two siblings sitting the exam see independent scores after publication, one grouped notice to their shared guardian, one-child correction reaches only eligible recipients. A stale batch fails without partial publication. **DoD** Inspect separation of schedule/results, numeric and scope checks, outbox and both clients' review; record builds.

### E07 — Produce scoped academic reports from current source records

**Goal / requirements** R09. Let families and staff inspect how a pupil's report was calculated for a subject and period. **Depends** A04, E02, E04, E05, E06. **Files** `reports`, `AcademicReportScreen`, migration `academic_report_sources`. **Scope** Academic evidence, independent from financial reports. Parents access only approved children and permitted source details.
- [x] Build scoped source query with sourceKind, sourceId, revision, offering/subject, class/year, schoolDate/period, visibility, numerator/max or scale and inclusion reason. Read A04 approved attendance; E02 taught log and activity scores; E03/04 assignments + recorded scores; E05 published evaluation dimensions; E06 published exam marks. Group by applicable period and subject; show attendance once per school day, independent from subject marks. Keep three evaluation scales independent. Retain original enrollment/class context across transfers.
- [x] Implement `GET /academics/reports/students/{id}?from=…&to=…&subjectId=…` → period, context, source rows, counts, inclusion/exclusion explanation and per-kind totals. Use arithmetic mean of recorded homework scores out of 20 (null excluded, 0 included); show activity/exam earned and possible for included marks with their units. Do not mix evaluation scales, attendance and marks into a fabricated weighted grade. Zero count means no recorded values. Changes to a published result must appear in detail and report from the same current revision as soon as the write commits. Any materialized cache must invalidate by affected child/subject/period in that transaction.
- [x] Build teacher class/pupil selectors and academic supervisor scoped search, parent child switcher with period/subject controls, accessible source breakdown and deep links that authorize again. Both clients indicate missing records, out-of-scope, loading and refreshed correction. Any export entry point uses the same projection, scope and redaction.

**Acceptance at final QA** For homework [null,0,10.5] show 2 scored, 5.25/20; exclude draft exam/evaluation and duplicate attendance, retain the approved activity mark/maximum. Correct 10.5 to 11 and observe 5.5/20 plus updated source revision. After unlink, a copied URL, search query, export or deep link cannot recover information. **DoD** Inspect source joins, denominator and scope logic, revision invalidation and both platform drill-downs; record builds.

# Identity, access and account implementation plan

> For agentic workers: use Superpowers executing-plans and the owner's cadence in [PLANS.md](../../../PLANS.md). Work through ready cards without requesting routine approval.

**Goal** A real person signs in once, works in an authorized school role and can recover access. Ending a relationship or a session promptly ends the corresponding access.

**Architecture and stack** Supabase Auth proves the identity. The Next.js BFF verifies the session, resolves current school grants and enters F02's scoped database transaction. The iPhone and desktop web clients share web sessions. Kotlin/Compose uses its own PKCE and bearer-token lifecycle. PostgreSQL owns permissions, people and invitation/application transitions. [Product](../specs/product.md) · [Integration contracts](../specs/contracts.md) · [Screen design](../specs/ui.md)

**Scope and sequence** R02 and R03, with R01/R04/R10/R15 integration. The baseline has README.md and the planning packet. All application code and database migrations named below are future files. Routes listed within a card are relative to `/api/v1`; the envelope, revisions, idempotency and status codes come from F02. Register each route in the F02 OpenAPI file. Migration file names below are suffixes under `supabase/migrations`; assign the ordered prefix during integration. Each card updates the existing tracking file PROGRESS.md with files, build result and pending final cases. Use the root build/static commands defined in PLANS.md. First test authoring and test execution take place in Q01 after the complete staging deployment.

**Review focus** A replaced email link opened on a second device, an email scanner opening a link before the person, a staff parent returning to a shared device, concurrent removal of the last administrator, and a revoked child link followed by a historical payer receipt. Acceptance cases below belong to Q02/Q03/Q06.

### I01 — Verify identities, switch personas and end sessions

**Goal / requirements** R02, R03. Associate one verified provider identity with one school account and derive F02's actor on every domain request. **Depends** F01, F02, F03.

**Scope** Sign-in, active persona, server actor and sign-out. Invitation and recovery lifecycles belong to I02/I04.

**Files** Planned `packages/contracts/src/identity.ts`, `apps/web/src/server/identity/{session,actor,provider}.ts`, `apps/web/src/app/api/v1/auth/`, `apps/web/src/app/[locale]/account/sign-in/page.tsx`, `apps/android/app/src/main/java/de/madrasty/app/identity/{SessionStore,AuthRepository,SignInScreen}.kt`, migration `identity_sessions.sql`.

**Interfaces and data** POST `/auth/sign-in {email,password}` (web cookie + CSRF binding); Android signs in through the configured Auth client and presents a verified bearer on GET `/auth/session`. Both read `{accountId,sessionId,personas,activePersona,assurance,expiresAt}` inside `data`, without password, tokens or grant secrets. POST `/auth/persona {persona}` returns the verified context for this session. POST `/auth/sign-out {allDevices:boolean}` terminates the selected scope and returns 204. Tables `app.account` (unique provider subject, status, authorization revision), `app.persona_grant` (unique account/persona, lifecycle) and `app.session_binding` (provider session id, account, active persona, expiry/revocation). Use `admin|teacher|guardian` wire identifiers; specialist office work uses an admin persona with explicit capabilities. A pending applicant may use only the authenticated application-status surface.

- [x] Bind the provider subject after verified email ownership and a valid school-controlled onboarding path. Require current issuer, audience, expiry, active provider session, active local binding and the selected persona on every domain request. Unlinked identities see only their allowed onboarding surface. Generic sign-in failures and throttling avoid disclosing whether an email exists.
- [x] Implement web sign-in with a secure server-managed cookie and CSRF/origin checks. Implement Android PKCE, rotating refresh tokens protected by Android Keystore, and an HTTPS App Link callback bound to the release host in D04. Validate redirect/state and use an allowlisted local destination. Offer a useful HTTPS continuation if the app is absent or the originating device holds the PKCE verifier.
- [x] Return only current persona options. Switch under a verified grant, sever the prior persona's device push association, clear prior tab stacks, pending actions, data/drafts, query subscriptions and protected media. Rebuild from the newly scoped home. Separate devices can retain different personas. Reject requests from stale screens carrying an old persona.
- [x] Warn before discarding unsent drafts. On confirmed logout remove local access immediately, invalidate the server binding/refresh capability and detach device push; terminate all selected bindings for all-device logout. Where connectivity fails, purge private local material, retain only minimal device revocation work, finish it at reconnection and never show a server-wide revocation confirmation prematurely. Check active session eligibility again at push dispatch.

**Acceptance / final cases** A staff parent sees only their own children in the guardian persona; replay from an old screen or revoked token cannot read that data. Shared-device logout removes suggestions, local roster, attachments and push binding for the old account. New install, expired session and browser-to-home-screen sign-in preserve only safe continuation state. **Checkpoint/DoD** `pnpm check:types`, `pnpm build:web`, `pnpm build:android` exit 0. Record auth origin and protected partition boundaries for Q02/Q03/Q06.

### I02 — Recover accounts, enforce admin MFA and protect the last administrator

**Goal / requirements** R02, R03. Establish the first administrator, maintain MFA for all staff using the admin persona, and provide safe succession, email changes, reset and deactivation. **Depends** I01.

**Scope** Recovery, admin assurance, bootstrap/succession and deactivation. Concrete class/child grants belong to their domain owners.

**Files** Planned `apps/web/src/server/identity/{recovery,assurance,staffLifecycle}.ts`, `apps/web/src/app/api/v1/{auth,staff}/`, `apps/web/src/app/[locale]/account/security/`, `apps/android/app/src/main/java/de/madrasty/app/identity/SecurityScreen.kt`, `scripts/identity/bootstrap-admin.ts`, migration `identity_lifecycle.sql`; extend I01 identity DTO and session verifier.

**Interfaces and data** POST `/auth/recovery/request {email,locale}` → 202 generic accepted; POST `/auth/recovery/complete {challenge,newPassword}` → 204 after valid provider recovery proof. POST `/auth/email-change {newEmail,reauthProof}` → 202; POST `/auth/email-change/confirm {challenge}` → 204. POST `/auth/mfa/enroll {}` → provider enrollment challenge; POST `/auth/mfa/challenge {factorId}` and `/auth/mfa/verify {challengeId,code}` → session assurance and verified time. POST `/staff/{id}/deactivate {scope,reason,revision}` → lifecycle revision; scope explicitly selects staff access or the whole account for an authorized lifecycle owner. Store lifecycle revisions, actor, reason and factor references; provider owns password/factor secrets. Recovery tokens, passwords and TOTP seeds never enter logs or audit.

- [x] Implement an operator-only initial-admin command bound to an environment and verified named recipient. Serialize the empty-school bootstrap, persist its pending grant once, complete possession verification and MFA before enabling administration. Rerun resumes the same pending grant or returns already initialized. Remove bootstrap credentials from normal runtime.
- [x] Require verified admin MFA for every administrative route, including delegated specialists. During enrollment grant access only to setup/recovery. Expose an assurance check with a fresh challenge for especially sensitive actions, consumed by the finance bank-change capability. Expired challenges or factor replacement require fresh verification.
- [x] Deliver expiring single-use reset through the configured provider, rate-limit requests and clear existing app sessions upon success. For an active email change, require current authentication plus independent verification of the new address through the provider; notify the previous address and keep the existing login until confirmation. Reject conflicting verified identity ownership.
- [x] Serialize every change that could leave zero active, fully enrolled administrators capable of managing access (disable, revoke, replace root grant or remove final required factor). Require a verified, active, MFA-capable successor before ordinary removal. Document restricted operator recovery in `docs/execution/identity-recovery.md`: named school approver, independently verified owner identity, authorized operator, audited provider factor recovery, re-enrollment and session revocation. Recovery restores the named account without a public bootstrap/reset bypass.
- [x] Show effective changes before deactivation. Staff-only deactivation revokes assignments/grants, invalidates active sessions and removes work directory/inbox access. Preserve a separately entitled guardian persona after fresh sign-in. Whole-account deactivation blocks all access. Persist a local deny state synchronously and queue retriable provider/session cleanup with idempotent reconciliation.

**Acceptance / final cases** Two concurrent last-admin removal attempts leave an enrolled capable administrator. Bootstrap interrupted after provider identity creation resumes exactly once. A lost-factor recovery restores MFA and invalidates the old session. Email changes leave other accounts' ownership intact. A disabled staff parent can use only separately active family access after reauthentication. **Checkpoint/DoD** Both builds and `pnpm check:types` exit 0; roles requiring step-up, lifecycle command and recovery ownership recorded for Q02/Q03/Q07.

### I03 — Authorize capabilities, objects and inboxes in a verified persona

**Goal / requirements** R03, R16. Enforce least privilege for reads and writes including list counts, search, export, private media and deep links. **Depends** F02, I01. School, communications and finance tasks bind their own relation-dependent policies when their tables exist.

**Scope** Central capability model, grant editor and query contracts. Domain-specific table policies are attached when their owning tables are introduced.

**Files** Planned `packages/contracts/src/capabilities.ts`, `apps/web/src/server/access/{capabilities,policies}.ts`, `apps/web/src/app/api/v1/staff/[id]/grants/route.ts`, `apps/web/src/app/[locale]/staff/access/`, `apps/android/app/src/main/java/de/madrasty/app/identity/StaffAccessScreen.kt`, migration `identity_permissions.sql`.

**Interfaces and data** GET `/staff/{id}/grants` → scoped grant summary and revision; PATCH `/staff/{id}/grants {revision,personas,capabilities,inboxAssignments}` → validated result. Only access-management administrators can grant; elevated grants use I02 assurance and last-admin rules once integrated. Define `authorize(actor, action, resource)` and the corresponding DB scope/query builders. `app.capability_grant(account_id,capability,valid_from,valid_until)` and inbox grant references separate persona, permission and assignment. F02's runtime role is subject to RLS; all table policies default deny until the owning module binds its predicates.

| Scope | Predicate carried into the owning query and RLS policy |
|---|---|
| Root administration and delegated offices | Active administrative persona + valid MFA + action grant. Student affairs manages links/enrollment/invites and its office inbox; academic supervision manages dated teaching/attendance/publication; accounting handles payer records, posting/settlement and finance inbox when assigned. Grants combine. Bank mutation additionally needs the separate bank permission and fresh assurance. |
| Teacher and substitute | Active teacher persona + effective class/subject/attendance responsibility for the school date and operation. Substitute access expires at the agreed end. A general teacher grant alone reveals no class. |
| Guardian | Active guardian persona + live child link for school records. Historical invoice/receipt access uses named payer ownership. Another linked guardian sees only their own payer records, private threads and individual settings. |
| Messaging | Direct threads and their media require current eligible participation; no role-wide private read, even for root. Official follow-ups require assigned inbox delegation on the appropriate office for staff, and the relevant participating account for family. Replacing a worker transfers assigned office work only. |

- [x] Implement fail-closed action resolution and F02 transaction-local actor binding. Produce a policy map with operation, date basis, persona, grant and object predicate. Declare the resource-scoping interface now and let school/finance/messaging own concrete joins and invalidation hooks in their migrations.
- [x] Use the same scoped query for list, count, search, export, attachment, details and actionable links. Conceal inaccessible object existence via 404, retain 403 for a known role action. Reauthorize before issuing private media access and before sends. Invalidate caches and pending deliveries when assignments, relationships, capabilities or persona expire/change.
- [x] Implement the staff grant editor with readable effective permissions, separate office inbox controls, MFA state and revision. Block self-escalation, unauthorized delegation and stale saves. Changing grants emits a minimal audited event and invalidates old authorization state.

**Acceptance / final cases** An accountant cannot open a private guardian–teacher chat by any entry point. An expired substitute cannot search a former class. A dual-role teacher cannot view unrelated pupils in guardian mode. A revoked family link removes student records, pending notifications and exports; a pre-existing invoice remains readable only by its named payer. **Checkpoint/DoD** `pnpm check:types` and both builds exit 0; policy ownership and scoped transaction signature recorded for Q03/Q05.

### I04 — Issue and redeem invitations after family links are committed

**Goal / requirements** R02, R03, R04. Invite an individual or an explicitly selected committed import batch and reconcile each recipient through activation. **Depends** I01, I03, S02 (family links), S04 (committed import recipients); teacher invite requires its own staff authority, independent of a family link.

**Scope** Staff-controlled invitation, verified activation and batch delivery status. School owns family relationship creation; C06 owns the shared delivery transport.

**Files** Planned `packages/contracts/src/invitations.ts`, `apps/web/src/server/identity/{invitations,inviteDelivery}.ts`, `apps/web/src/app/api/v1/invitations/`, `apps/web/src/app/[locale]/{invite,staff/invitations}/`, `apps/android/app/src/main/java/de/madrasty/app/identity/InvitationScreens.kt`, migration `identity_invitations.sql`.

**Interfaces and data** GET `/invitations?batchId=&status=&cursor=` → authorized recipients/status/revision; POST `/invitations {recipientId,kind,locale}`; POST `/invitations/batches {committedBatchId,recipientIds}` → accepted recipient counts + operation ID. POST `/invitations/{id}/reissue {revision,correctedEmail?}` → replacement status; POST `/invitations/redeem {token}` with verified provider ownership matching the recipient → account/persona. Require Idempotency-Key for issuance/reissue/redemption. Store recipient kind, stable recipient id, optional committed batch id, normalized ownership email, hashed opaque proof, generation, expiry and consumption/invalidated timestamps. Delivery `ready|queued|sent|bounced` and validity `pending|expired|replaced|revoked|activated` are distinct. A sent email is acknowledged by the provider; activation is an account event.

- [x] For manual guardian invitations require an existing guardian record with an approved active child link. For imports select stored S04 recipients by committed batch ID, recheck eligibility and preview counts, language and conflicts. An import preview or file upload has no sending path. Deduplicate by stable recipient and pending generation, including duplicates across two children or reimported files.
- [x] In one command commit the token generation, minimal audit and invitation.dispatch_requested outbox record for C06. The event carries only invite ID/generation and restricted recipient reference; the worker privately resolves the proof. Store only a hash for lookup; protect any short-lived secret needed by the private mail dispatcher, purge it after delivery/expiry and redact it from link analytics, logs and referrers. Retry the same unique generation/reconcile unknown provider acceptance. Reissue atomically invalidates old generations. Correlate provider bounce to the exact delivery attempt. Correcting a pending contact never silently changes an active account's verified address.
- [x] GET of the HTTPS link displays a language-aware landing page; link scanners cannot consume it. For a new adult, the restricted Auth adapter creates or reuses a pending provider identity. Generate the provider email-verification invitation proof server-side and deliver it in the same school invitation via C06. A deliberate continuation exchanges the proof through the provider, opens a limited activation session and prompts the adult to choose and confirm a password using the provider password-update route. Do not pre-confirm a new email, send passwords or grant access to child data until claim succeeds. An existing verified adult signs in and confirms the new role/link using the same identity. Recover an interrupted provider step with reissue/sign-in, without duplicating accounts. A deliberate POST after identity verification binds the immutable subject and recipient exactly once with an atomic compare/update. Android verified links and the HTTPS fallback reach the same continuation, including on a second device. Expired/replaced/consumed/mismatched or revoked relationships reveal no child data and offer a route to assistance.
- [x] A verified active guardian with a newly approved link gets a single relationship notification instead of another credential invitation. Suppress it on replay and cancel pending work after revocation. Build the staff invitation worklist (ready/sent/bounced/expired/activated), single-recipient recovery and accessible status screens in Arabic and German.

**Acceptance / final cases** Two imports, two children and retries yield one pending invite for the same adult. A clicked scanner link remains usable. Resend invalidates the old link, expiry is enforced at claim, and concurrent redeem creates one binding. A corrected bounce reaches the corrected eligible person. A revoked link before dispatch suppresses mail and claim. **Checkpoint/DoD** `pnpm check:types` and both builds exit 0; record whether recipient identity came from manual registration or S04 and how recovery surfaces link, for Q02/Q03/Q06.

### I05 — Submit, review and follow teacher applications

**Goal / requirements** R02, R03. Let an applicant see a real decision from their verified account, and let authorized staff review applications. **Depends** I01, I03, I04 for optional staff-initiated invitation entry.

**Scope** Teacher application, decision and applicant status. Teaching assignments and substitute dates belong to S05.

**Files** Planned `packages/contracts/src/teacherApplications.ts`, `apps/web/src/server/identity/teacherApplications.ts`, `apps/web/src/app/api/v1/teacher-applications/`, `apps/web/src/app/[locale]/{apply,staff/applications}/`, `apps/android/app/src/main/java/de/madrasty/app/identity/TeacherApplicationScreens.kt`, migration `teacher_applications.sql`.

**Interfaces and data** POST `/teacher-applications {displayName,workContact?,requestedSubjects?,correspondenceLocale}` → application id, `submitted`, revision. GET `/teacher-applications/me` → applicant-visible status/decision date; GET `/teacher-applications?status=&cursor=` → authorized review queue; POST `/teacher-applications/{id}/decision {decision,revision,applicantMessage?}` → `approved|declined`, revision. Persist verified account id, state, dates, reviewer and applicant-visible decision message separately from staff-only notes. Unique active submission per applicant.

- [ ] Add a teacher application entry to the public sign-in page with email verification, including account sign-in for an existing guardian applicant. Scope the authenticated status surface to the applicant. Submitted/declined states cannot open school data. Preserve unrelated family access.
- [ ] Implement a revision-checked review decision under staff access-management authority. Approval grants a teacher persona exactly once, with zero class access until assigned. Decline adds no grant. A staff-created teacher may instead redeem a personal I04 invitation. Keep identity and teaching assignments independent.
- [ ] Provide native/web entry, form validation, pending status, decision date and optional applicant-facing message, with retry preserving input. Refresh status after sign-in or returning via an authorized notification; enqueue teacher_application.decided with application ID, verified applicant account, decision and revision on the state transition. C07 projects the applicant-scoped in-app notice; private reviewer notes never enter the event.

**Acceptance / final cases** An applicant returns on the second device to the actual pending/approved/declined state. A different signed-in account cannot retrieve it. Two staff decisions with the same revision produce a single decision and notification; a pending/approved-but-unassigned applicant sees no pupil records. **Checkpoint/DoD** Both builds and `pnpm check:types` exit 0; record transition and grant ownership for Q02/Q03.

### I06 — Manage preferences and browse permitted work contacts

**Goal / requirements** R01, R02, R03, R10. Let each person choose their experience and reach the right school contact within the active persona. **Depends** I01–I03, S02 and S05. The directory consumes S05's eligible work contact projection and dated assignments. C01 consumes these routes to start/resume chats.

**Scope** Account preferences and read-only eligible contact directory. S05 owns staff records, C01 opens conversations and C05 records device subscriptions.

**Files** Planned `packages/contracts/src/account.ts`, `apps/web/src/server/identity/{preferences,directory}.ts`, `apps/web/src/app/api/v1/{account/preferences,directory}/`, `apps/web/src/app/[locale]/{account/preferences,directory}/`, `apps/android/app/src/main/java/de/madrasty/app/identity/{AccountScreen,DirectoryScreen}.kt`, migration `account_preferences_directory.sql`.

**Interfaces and data** GET/PATCH `/account/preferences` with `{uiLocale,correspondenceLocale,theme,revision}`; locales `ar|de`, theme `system|light|dark`. GET `/directory?query=&role=&cursor=` → authorized work contacts and reachable official inboxes; GET `/directory/{id}` → display name, work role, permitted context, optional designated work email/phone and permitted action descriptors. Keep private login/recovery addresses and private telephone numbers outside the work directory. Store work contacts as explicitly published work fields; each account has its own preference record.

- [ ] Put account, persona, language, appearance, notification settings, security and sign-out under More. Link push opt-in to the device's explicit user gesture and device settings; server-side language changes do not imply OS permission. Show UI and correspondence language as separate fields and preserve both across sessions.
- [ ] Serve only currently eligible active contacts. A guardian sees work contacts for all active administrative staff and only teachers currently teaching their linked children. Search by name or job inside the same policy as list/detail. Teacher/staff lookups stay within the authorized work context, and omitted email/phone rows offer no inferred value. Distinguish the named person's private conversation from a delegated office inbox.
- [ ] Expose approved contact actions to messaging (explicit person target vs official inbox and permitted record reference). Use accessible email/phone actions only when work values are present. Preserve navigation context across return to child or class and clear it on persona changes. Disable deep links and evict stale results when school links or assignments are revoked.

**Acceptance / final cases** Arabic UI with German email stays that way across re-login. A sibling's teacher appears only while the relevant assignment/link is active. Revoked contacts vanish on detail, search and direct navigation. Missing work telephone has no call action. Arabic and German names, long titles and large text remain readable. **Checkpoint/DoD** Both builds and `pnpm check:types` exit 0; record directory and account routes for Q02/Q03/Q05/Q06.
